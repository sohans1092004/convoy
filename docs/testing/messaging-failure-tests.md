# Messaging failure tests (PLAN §4.3.5) — specified in P0, implemented in P2

Common harness: Testcontainers PostgreSQL 16 + LocalStack (SNS/SQS) + the real outbox relay and inbox consumer libraries, driven through the **pool → payment** and **pool → realtime/notification** paths unless stated. Fault injection uses (a) a `FaultPoint` hook compiled only into the `test` profile (`FaultPoints.crashAt("relay.afterPublish")` throws `SimulatedCrash` and kills the worker thread/JVM container), (b) container kill/pause via the Docker API, (c) Toxiproxy between services and LocalStack for latency/cut. Every test asserts the global invariants at the end:
- **I-1** no event lost: every outbox row has `delivered_at` set and every subscribed consumer has exactly one inbox row per event_id;
- **I-2** no duplicate business effect (counts, refunds, ledger entries exactly once);
- **I-3** ledger invariants (deposit-contract.md §5) hold;
- **I-4** DLQs empty unless the test expects a poison message.

| # | Scenario | Setup | Fault injection | Expected observable result | Pass criteria |
|---|---|---|---|---|---|
| MF-1 | Commit, then crash before publish | Buyer commits; pool writes membership + outbox row (MemberCommitted) | `FaultPoint relay.beforePublish` kills the relay process after the business transaction committed and before `sns.publish` | After relay restart the row is published; realtime/notification/audit receive MemberCommitted once; pool counts correct | I-1..I-4; publish latency after restart < 5 s; outbox row `attempts = 1` after restart |
| MF-2 | Broker accepted, relay crashed before marking delivered | Same as MF-1 | `FaultPoint relay.afterPublish` crashes after SNS ack, before `UPDATE outbox SET delivered_at` | Event is published twice (same event_id); each consumer applies it once, second delivery counted as duplicate (metric `inbox_duplicates_total{consumer}` += 1) | I-1..I-4; exactly one effect per consumer; duplicate counter = 1 per consumer |
| MF-3 | Consumer committed, crashed before acknowledging | payment consumes MemberLeft → creates refund | `FaultPoint consumer.afterCommitBeforeAck` kills consumer after the DB transaction (refund + inbox row) and before `DeleteMessage` | Message becomes visible after visibility timeout (set to 10 s in test), is redelivered, rejected by inbox unique key, acked | One refund row, one RefundRequested outbox row; I-2; duplicate counter = 1 |
| MF-4 | Two events for the same pool out of order | Pool emits MemberCommitted (v=7) and MemberLeft (v=8) | Test publisher injects v=8 before v=7 directly into the realtime consumer queue (bypassing FIFO) and, separately, into a standard queue consumer | Consumer parks v=8 (gap), applies v=7, then v=8; a replayed v=6 is ignored as stale (`stale_events_total` += 1); if v=7 never arrives, after 5 min (1 s in test via config) consumer fetches the pool snapshot and resumes from it | Final consumer state = owner snapshot at v=8; no state regression; metrics as stated |
| MF-5 | Poison message | Any consumer queue with maxReceiveCount = 5 | Publish a message whose payload fails schema validation (or a handler that throws deterministically for one event_id) | Message retried 5 times then moved to DLQ; alarm `DLQ_NOT_EMPTY` fires (CloudWatch alarm in AWS, metric assertion in test); other messages keep flowing (no head-of-line blocking on standard queues; on FIFO the group is blocked — documented and asserted only for that pool_id group) | DLQ depth = 1; other aggregates' events processed; runbook redrive after fix delivers it exactly once |
| MF-6 | Consumer offline for hours, then replays backlog | notification consumer stopped | Stop consumer; generate 50,000 events over 2 h simulated (accelerated in test: 50,000 events, consumer stopped 30 min); restart | Backlog drains in order of arrival (standard queue: no global order; per-aggregate version checks prevent regressions); oldest-message-age decreases monotonically after restart; no message older than SQS retention is lost (test asserts retention ≥ backlog age); for > retention case, outbox re-publish job by time range restores missing events | All 50,000 processed exactly once (I-1, I-2); drain time and peak oldest-message-age recorded; audit count reconciliation passes |

Recorded per run: commit hash, environment (local/LocalStack or AWS), queue settings (visibility timeout, maxReceiveCount, retention), counts, durations.
